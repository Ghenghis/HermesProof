# Release pointers — closing the OTA auto-activation trust gap

## The gap this closes

The managed updater (`src/updater/managed-updater.mjs` + `git-source.mjs` + `release-verifier.mjs`)
resolves an update channel to a commit SHA via `git ls-remote` against the allowlisted GitLab
remote, stages that exact SHA, and runs 9 gates (`CANDIDATE_REQUIRED_GATES` in `release-verifier.mjs`)
against the checked-out candidate — including running the candidate's *own* `npm test`. Until this
change, **that was the entire trust basis for auto-activating a release**: any commit that lands on
the tracked branch, and whose own test suite passes, can be auto-activated. There was no independent
cryptographic signature check anywhere in this path (the existing Ed25519 signer in
`src/core/release-signing.mjs` is only wired into the *packaged Windows ZIP* distribution channel via
`scripts/verify-hermesproof-release.mjs`, never into the git-based self-updater).

Two independent fixes landed for this:

1. **Anti-rollback check** (`git-source.mjs`'s `stage()`): a candidate is now rejected unless it is a
   fast-forward descendant of the currently-active release (`git merge-base --is-ancestor`). This is
   always on, no configuration needed. It stops a channel ref that resolves back to an older,
   previously-good SHA from being silently re-activated.
2. **Release pointers** (`src/core/release-pointer.mjs` + a new, opt-in
   `"release-pointer-signature"` gate in `production-gates.mjs`): an explicit, offline-signed
   statement that "commit X is blessed for auto-activation on channel Y," checked with the *same*
   Ed25519 key already used to sign packaged releases.

## Why release pointers are a *local* file, not something committed to the repo

A pointer for commit X cannot be part of commit X's own tree — adding the pointer would change the
tree, which changes the commit's hash, which no longer matches what the pointer names. This isn't a
bug to work around; it's why every trust-bootstrap scheme with this shape (SSH's `authorized_keys`, a
manually-seeded TUF `root.json`) treats the trust statement as separate, out-of-band, operator-held
configuration rather than versioned source.

So a release pointer lives at `<managedRoot>/trust/release-pointer-<channel>.json` on **each machine**
that should auto-activate that channel — not in git. You (the person holding the offline private key)
decide when a commit is safe to bless, sign it once, and copy the resulting file to whichever
machines should trust it.

## Current status: built and tested, **not yet turned on**

`"release-pointer-signature"` exists as a real gate function (see `production-gates.mjs`) and has full
test coverage (`src/core/release-pointer.test.mjs`, plus the gate-level tests in
`src/updater/production-gates.test.mjs`), but it is **deliberately not** in `CANDIDATE_REQUIRED_GATES`
(`release-verifier.mjs`) yet. Adding it there is a one-line change — but doing so before a pointer has
ever been signed for the active channel means **every future `apply()` fails closed** (no valid
pointer = no activation), by design: an unblessed candidate must never silently auto-activate. That is
correct fail-closed behavior, not a bug, but it's a real operational step, not just a code change, so
it's being called out explicitly rather than flipped silently.

### To turn it on

1. Decide the channel's current HEAD SHA is safe: `git ls-remote https://gitlab.com/Ghenghis/HermesProof.git refs/heads/main`.
2. Sign it with your existing offline release-signing private key (the one that produced
   `config/hermesproof-release-ed25519-public.pem`):
   ```
   node scripts/sign-release-pointer.mjs --sha <that sha> --channel stable --private-key <path to your offline key>
   ```
3. Copy the resulting file to `<managedRoot>/trust/release-pointer-stable.json` on every machine that
   should enforce it (`managedRoot` defaults to `~/.hermesproof-managed`).
4. Add `"release-pointer-signature"` to `CANDIDATE_REQUIRED_GATES` in `src/updater/release-verifier.mjs`.
5. Each time you want to bless a new commit going forward, repeat steps 1–3 for that machine.

**This private key must never be generated by, or made accessible to, an AI coding agent** — the
entire point of this mechanism is that a commit (including one an agent authored or that an agent's
own compromised session pushed) cannot activate itself; that only holds if the signing key stays
outside any agent's reach.
