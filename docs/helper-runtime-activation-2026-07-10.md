# Helper Runtime Activation — 2026-07-10

This record is an operational checkpoint for the local HermesProof helper layer. It is not KiloCode release proof and it does not close any KiloCode gate.

## Scope

The local helper topology is intentionally narrow:

| Component | Current role | Authority boundary |
|---|---|---|
| ZeroClaw local | Bounded local health and future Windows-focused helper tasks | Cannot accept a gate or release on its own. |
| HermesAgent bridge | MiniMax M3 diagnosis/research helper with DeepSeek fallback | Cannot accept a gate, self-authorize work, or bypass HermesProof. |
| HermesProof | Evidence, policy, envelope validation, and final acceptance | Requires real runner, artifact, and `ev_*` evidence. |

No helper is configured as a background service in this checkpoint.

## ZeroClaw V3 Configuration Finding

ZeroClaw V3 requires a provider, an agent, and a named risk profile. The installed `0.8.2` CLI accepted scalar configuration for the provider and agent but rejected creation of a dynamic `risk_profiles.<alias>` map entry through both `config set` and `config patch`.

The canonical V3 form generated by the same binary uses `[risk_profiles.<alias>]`; that form passed all nine local no-network self-checks once added to the disposable profile. The production local profile now uses the same canonical, supervised block. This is an upstream CLI limitation to preserve in future activation work, not a reason to omit the risk profile.

## HermesAgent Bridge Health

HermesProof's `HermesAgentBridge` is a bounded direct provider helper. It is distinct from the separately installed Hermes CLI application. An isolated current-source HermesProof MCP server was started with the approved configuration and proved:

| Check | Result |
|---|---|
| Current helper evaluator tool advertised | Yes |
| HermesAgent health tool advertised | Yes |
| Primary provider reachable | MiniMax |
| Model used | `MiniMax-M3` |
| DeepSeek | Configured only as fallback |
| Timeout/error signal | None during the health probe |

The MCP process reads `HERMES_AGENT_ENABLED`, provider order, model selection, scope, and goals when it starts. A client session that began before this activation can continue to expose the older tool list or report `bridge disabled`; it must be restarted rather than treated as a failed provider health result.

The separately installed Hermes CLI's `--version` command performs a synchronous update check, including a Git fetch. It is not used by `HermesAgentBridge` and is not a valid bounded HermesProof health probe. Do not substitute it for bridge health or KiloCode gate evidence.

## Required Startup Contract

Start the HermesProof MCP process with these non-secret settings and the existing private environment loader:

```text
HERMES_AGENT_ENABLED=1
HERMES_AGENT_FAILOVER=minimax,deepseek
MINIMAX_MODEL=MiniMax-M3
HERMES_AGENT_SCOPE=resolve_blocked,post_stream_message
HERMES_AGENT_PROJECT_GOALS=<bounded project goals>
```

The private loader supplies the named MiniMax and DeepSeek key variables only to the spawned process. Never place key values in MCP configuration, repository files, logs, or evidence.

## KiloCode Handoff Order

1. Restart the consuming MCP host so it loads the current HermesProof server and startup contract.
2. Confirm `hermes_agent_health` returns a MiniMax M3 health result and `hermes_helper_runtime_evaluate` is present.
3. Attach the verified HermesProof MCP startup contract to KiloCode.
4. Run only focused KiloCode UI-driver proofs with a matching helper preflight and envelope.
5. Preserve blocked results as blocked; promote no release claim until the strict KiloCode release command passes.
