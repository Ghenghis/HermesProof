# RC26.4 Prime Agent Integration Design

**HermesProof target:** v0.9.1 (`dee988b`)  
**Prime Agent target:** v0.7.2 (`83a0f9f` from PrimeIntellect upstream; Ghenghis fork baseline)  
**Design date:** 2026-08-16  
**Owner:** `claude-lead`  
**Verdict:** Ship a focused 10-day integration spike for RC26.4, gated by two green end-to-end proofs. Defer a hard, always-on control-plane coupling until RC26.5 so that RC26.4 stays shippable and the release manager can cut without landing an unproven agent runtime inside the core loop.

---

## 1. Executive summary

This document scopes how HermesProof can use Prime Agent as an external, daemon-backed, long-running worker for tasks that exceed the synchronous, one-turn-at-a-time model of Claude/Codex/Windsurf. Prime Agent v0.7.2 is an open-source RLM coding agent with a persistent IPython kernel, built-in subagent spawning (`rlm(...)`), a JSON/RPC line protocol, background sessions, heartbeats, and schedules. HermesProof v0.9.1 is a two-MCP-server coordination and proof layer that owns file locks, task queues, evidence ledgers, release gates, and project contracts.

The proposed integration does not put Prime Agent inside the HermesProof MCP server. Instead, HermesProof acquires a Prime Agent session as a **claimed, evidence-backed subagent worker**: the Prime Agent daemon runs in a separate process with its own security boundary, while HermesProof translates task queue entries to `prime-agent --mode json`/`--mode rpc` prompts, consumes the JSONL event stream, and writes Prime Agent outputs into the HermesProof evidence ledger before releasing the lock.

**Scope for RC26.4:** a narrow adapter surface that lets HermesProof `hermes_enqueue_task` / `hermes_pick_task` launch a long-running Prime Agent for well-defined work (research, documentation, test repair, or plan execution) and have the result chained back as `ev_prime_agent_*` evidence. No in-IDE UI changes, no replacement of `hermes3d-locks`, no ungated write permissions for the Prime Agent runtime.

## 2. Target system snapshots

### 2.1 HermesProof v0.9.1

- Two stdio-JSON-RPC MCP servers per workspace: `hermes3d-locks` (121 coordination/proof tools) and `hp-mha-serena` (34 composite/harness tools).
- File-backed durable state under `.hermes3d_orchestrator/`: locks, task queue, inboxes, project contracts, anti-slop reviews, claim audits, bug tickets, and the hash-chained evidence ledger.
- Six-stage edit pipeline: intent -> claim -> work -> optional handoff -> verify (gate) -> attest + release.
- Passive event and task queues; HermesProof never auto-calls an LLM API.
- `hermes_run_gate` runs allowlisted commands and captures output as evidence.
- `hermes_claim_task` / `hermes_lock_files` provide atomic, TTL-based ownership.

### 2.2 Prime Agent v0.7.2

- Self-improving RLM coding agent built on persistent IPython and a Continual Harness.
- `prime-agent --mode json` streams `AgentSessionEvent` JSON lines (session, agent_start/turn/message/tool/execution events, compaction, retry).
- `prime-agent --mode rpc` exposes bidirectional JSONL stdin/stdout commands: `prompt`, `steer`, `follow_up`, `abort`, `new_session`, `get_state`, `get_messages`, `bash`, `set_model`, `send_message`, `observe`, schedule/heartbeat management, and session management.
- Daemon/supervisor/worker architecture: the daemon owns discovery/routing; each worker owns a root `AgentSession`, scheduler, and IPython kernel; child RLM runtimes can be spawned.
- Sessions run in the background, can be reattached, and agents can send `agent_message.send` to one another.
- v0.7.2 release notes: mostly UI/UX fixes, worker lifecycle hardening (stopping/zombie workers, stale registration self-heal), privacy-safe analytics, and in-place queued-message editing.

### 2.3 Delta between the two systems

| Dimension | HermesProof | Prime Agent | Integration concern |
|---|---|---|---|
| **Time model** | Synchronous, turn-scoped, waits for agent | Asynchronous, daemon, heartbeats, schedules | Need a bridge that holds a claim across long work |
| **State model** | File-backed, append-only, git-anchored | Session JSONL + harness prompts, mutable per session | Prime Agent is not the source of truth; final artifacts must be committed and attested |
| **Security** | User OS permissions, lock gates | Model-generated Python can run arbitrary code | Must isolate Prime Agent in a bounded worktree and drop write rights except to a scratch/staging area |
| **Coordination** | 155 MCP tools, explicit locks | Built-in agent-to-agent messages and subagents | Do not replace HermesProof locks; wrap them as tool calls from Prime Agent skills |
| **Evidence** | Hash-chained NDJSON ledger | Transcript JSONL + summaries | Merge Prime Agent JSONL transcript excerpts into HermesProof `evidence/ev_*.ndjson` |

## 3. Prime Agent capability matrix for HermesProof

| Capability | v0.7.2 support | HermesProof RC26.4 use | Implementation fit |
|---|---|---|---|
| Long-running background sessions | Yes (daemon + worker) | Execute multi-hour research/repair tasks | High: use `prime-agent --mode rpc` and `hermes_heartbeat` to keep lock alive |
| `rlm(...)` subagents | Yes | Parallel sub-investigations under one hermes task | Medium: HermesProof task is the root; child Prime Agents are spawned inside the same worker |
| JSON/RPC event stream | Yes | HermesProof bridge consumes `tool_execution_end`, `message_end`, `turn_end` | High: bridge parses JSONL and writes `ev_prime_agent_*` |
| `bash` tool execution | Yes | Run hermes gates from inside Prime Agent | High:Prime Agent `bash` results become `BashExecutionMessage`; use `bash` only to call allowlisted `hermes_run_gate` wrapper |
| IPython tool environment | Yes | Python helpers for analysis, metrics, AST | Medium: useful but not required for RC26.4 |
| `/refine` harness updates | Yes | Could teach Prime Agent a project-specific skill for HermesProof | Defer: would require a skill package and a trust review |
| Schedules / heartbeats | Yes | Re-entrant periodic work (e.g. nightly test triage) | Medium: schedule lives in Prime Agent daemon; HermesProof stores the schedule pointer in task queue metadata |
| Agent-to-agent `send_message` | Yes | Cross-agent coordination | Defer RC26.4: out of scope; could be used in RC26.5 for supervisor swarm |

## 4. Five integration patterns compared

| # | Pattern | What it looks like | Verdict | Risks |
|---|---|---|---|---|
| 1 | **File watcher bridge** | Prime Agent watches `.hermes3d_orchestrator/events/outbox/` and reacts to events on its own. | **Reject** | Bypasses locks, creates evidence gaps, no task claim, hard to audit. |
| 2 | **MCP-in-Prime** | A Prime Agent skill implements `hermes_*` as Python functions that call the HermesProof core server. | **Defer** | Requires Prime Agent to speak MCP over stdio or HTTP; tool surface of 155 is too large to trust to an autonomous RLM. |
| 3 | **HermesProof MCP tool shim** | Add `hermes_prime_agent_run` and `hermes_prime_agent_status` to `hermes3d-locks`. Synchronous calls wait for full Prime Agent completion. | **Defer** | Breaks the synchronous MCP contract because sessions can run hours; would hold the LLM thread open. |
| 4 | **Task-queue subagent bridge (recommended)** | HermesProof enqueues a task with `taskType: "prime-agent"`. A dedicated `hermes-prime-agent-bridge` worker picks it, leases a Prime Agent session, streams JSONL, and appends evidence. | **Adopt for RC26.4** | Keeps HermesProof as the lock/evidence source of truth; Prime Agent is a worker; async by design; fits existing `hermes_pick_task`. |
| 5 | **Peer daemon bus** | HermesProof and Prime Agent share a bi-directional event bus and send each other messages freely. | **Defer to RC26.5** | Removes the one-turn-at-a-time discipline; no stable source of truth; security surface too large. |

### 4.1 Recommended pattern: Task-queue subagent bridge

Components:

1. **`src/prime-agent/bridge.mjs`** (new): a long-lived Node process that polls `hermes_pick_task` with `taskType: "prime-agent"`. When it picks a task, it calls `hermes_lock_files` for a scratch workspace, spawns `prime-agent --mode rpc`, translates JSONL events to evidence, writes final artifacts, then `hermes_release_files` and `hermes_complete_work`.
2. **`hermes_prime_agent` gate profile** (new): an allowlist of commands the bridge can run on the Prime Agent host (e.g. `prime-agent --mode json`, `node`, `git`, `npm run docs:check`).
3. **`ev_prime_agent_*` evidence schema** (new): append-only entries for `session_start`, `prompt_sent`, `tool_execution_end`, `turn_end`, `message_end`, `session_closed`.
4. **`docs/superpowers/plans/rc26.4-prime-agent-spike.md`** (new): a 10-day cut plan with two green E2E proofs before merge.

## 5. TypeScript adapter interface

```typescript
// src/prime-agent/types.ts

interface PrimeAgentTask {
  taskId: string;
  owner: string;
  workspaceRoot: string;
  scratchRoot: string;            // isolated clone/branch for the Prime Agent
  prompt: string;                 // initial user prompt
  followUps?: string[];           // queued follow-ups
  model?: Model;                  // optional set_model
  thinkingLevel?: ThinkingLevel;  // optional set_thinking_level
  deliveryMode?: "steer" | "follow_up" | "auto";
  maxTurns?: number;              // safety guard
  maxCostUsd?: number;            // safety guard
  evidenceTags?: string[];        // e.g. ["rc26.4", "prime-agent"]
}

interface PrimeAgentBridge {
  // lifecycle
  start(): Promise<void>;
  stop(): Promise<void>;

  // One task = one Prime Agent RPC session
  runTask(task: PrimeAgentTask): Promise<PrimeAgentResult>;
}

interface PrimeAgentResult {
  ok: boolean;
  sessionFile: string;             // Prime Agent JSONL transcript path
  hermesEvidenceIds: string[];     // ev_<id> rows written by the bridge
  artifactPaths: string[];         // files the bridge moved into HermesProof workspace
  cost: { input: number; output: number; total: number };
  error?: string;
}

// HermesProof side
interface HermesPrimeGateInput {
  command: "prime-agent";
  args: ["--mode", "json" | "rpc", "--cwd", string, "--prompt", string];
  env: { HERMES_TASK_ID: string; HERMES_OWNER: string };
}
```

The bridge is deliberately thin. All HermesProof coordination (claim, lock, heartbeat, evidence, release) happens through existing `hermes3d-locks` tool calls; the bridge is a trusted, single-purpose worker that happens to drive Prime Agent instead of a human.

## 6. HermesProof contract additions for RC26.4

Add the following to the project truth contract (default: `project-truth-contract`):

- `requiredGates`: `prime-agent-bridge-smoke` (starts the bridge and checks daemon health) and `prime-agent-e2e` (runs a known prompt through the bridge and verifies the artifact + evidence chain).
- `protectedPaths`:
  - `src/prime-agent/`
  - `docs/superpowers/plans/rc26.4-prime-agent-spike.md`
  - `.hermes3d_orchestrator/evidence/*prime-agent*`
- `requiredEvidence`: at least one `ev_prime_agent_session_start` and one `ev_prime_agent_turn_end` per Prime Agent task.
- `forbiddenClaimPatterns`:
  - "Prime Agent may write directly to `src/` outside a hermes lock."
  - "Prime Agent can bypass `hermes_run_gate` for production changes."

## 8. Risk matrix (9)

| Rank | Risk | Severity | Mitigation |
|---|---|---|---|
| 1 | **Arbitrary code execution** in Prime Agent IPython | Critical | Run inside a disposable worktree; bridge uses `hermes_lock_files` so Prime Agent only touches owned paths; model has no direct access to `src/` outside the scratch root. |
| 2 | **Evidence gaps** if the bridge crashes mid-session | High | Bridge appends `ev_prime_agent_*` per event, not just at the end; use Prime Agent `session.jsonl` as a recoverable transcript. |
| 3 | **Long-running lock TTL** expires before work completes | High | Bridge calls `hermes_heartbeat` every 5 minutes; initial `ttlMinutes` raised to 240 for Prime Agent tasks. |
| 4 | **Token/cost overrun** for open-ended prompts | High | `maxTurns` and `maxCostUsd` guards in the bridge; `set_auto_compaction` enabled; `/autonomous` not used in RC26.4. |
| 5 | **Version skew** between Prime Agent v0.7.2 and future v0.8+ | Medium | Pin `prime-agent_version` in task metadata; treat minor version bumps as contract changes. |
| 6 | **State drift** if Prime Agent edits the same files as a human/Codex | Medium | Bridge acquires `hermes_lock_files` before spawning the session; no edits outside the lock. |
| 7 | **Worker zombie/leak** if `stop` is not clean (v0.7.2 had worker-stop fixes) | Medium | Bridge registers a `finally`/`shutdown` handler; `prime-agent shutdown --force` on bridge exit; test with v0.7.2. |
| 8 | **Dependency on Node/Python local environment** for the bridge | Medium | Bundle as `src/prime-agent/bridge.mjs` (no build step); require `prime-agent` to be installed by the user; add `doctor` gate that checks `prime-agent --version`. |
| 9 | **Legal/telemetry** from v0.7.2's new privacy-safe analytics | Low | Document the analytics, provide a config path to disable, and do not include telemetry data in HermesProof evidence. |

## 9. Security boundary

```
User / Claude / Codex / Windsurf
         |
   hermes3d-locks (MCP stdio)
         |
   Task queue + lock manager + evidence ledger
         |
   hermes-prime-agent-bridge (Node process, single-purpose)
         |
   prime-agent daemon/supervisor (local OS process)
         |
   Prime Agent worker + IPython kernel (scratch worktree only)
```

- The bridge is the only component that holds both a HermesProof lock and a Prime Agent session lease.
- Prime Agent never sees the user's full project; it sees a scratch clone/branch created by the bridge.
- Model-generated `bash` and IPython code run as the bridge OS user, not as root, and with no secrets except read-only copies of what the task needs.
- After the session, the bridge copies the minimal result set into the HermesProof workspace and releases the lock. The scratch directory is archived or deleted.

## 10. Five-step rollback plan

1. **Gate kill switch**: `hermes_set_test_mode testing` disables `prime-agent-*` gates and the bridge stops picking new Prime Agent tasks.
2. **Bridge shutdown**: `prime-agent shutdown --force` from the bridge and `hermes_recover_stale_locks` to clear any stuck Prime Agent locks.
3. **State reset**: delete `.hermes3d_orchestrator/tasks/claimed/` entries owned by `prime-agent-bridge`; restore from the last evidence hash before the first `ev_prime_agent_session_start`.
4. **Code revert**: `git revert` the RC26.4 merge commit (only `src/prime-agent/`, contract, and docs changes).
5. **Artifact cleanup**: remove any `ev_prime_agent_*` evidence rows that are not pinned to a release; the append-only ledger remains intact, but non-pinned rows can be quarantined per `hermes_hp_mha_trace_prune` retention rules.
